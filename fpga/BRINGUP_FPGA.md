# DINO FPGA bring-up bible

The sit-down-and-flash companion for the Lattice ECP5-5G Versa
Development Board (LFE5UM5G-45F, CABGA381). Same shape as
`../tests/dino_bringup/BRINGUP.md` (the bench bible): what to flash, what
the LEDs must show, what a divergence means. This board is not a stand-in
for the bench — `fpga/top/versa_top.vhd` and `fpga/top/versa.lpf` are
generated-from-the-same-source fabric, and a bench-vs-FPGA divergence on
the same image is a finding about the *bench wiring*, not the fabric (see
"What the fabric tells the bench" below).

Every number in this document comes from a command shown next to it —
`python3 docs/notes/progrom_gen.py --expected`, a build log, or `--list-
boards` — never retyped by hand. Regenerate rather than trust stale
digits here.

## Toolchain — verified this session, not assumed

Build (from repo root):

    make -C fpga bit IMAGE=<tag>          # one image -> fpga/build/dino_<tag>.bit
    make -C fpga bits                     # the eight COVERAGE-tag images in one shot
    make -C fpga bit IMAGE=cylon          # the ninth, non-coverage soak image

`IMAGE_TAGS` (`fpga/Makefile`) is now `real in alu mem flow loop mardisc
pads` — mardisc and pads were added this task (previously only six).
`cylon` is not a member (it is not in `progrom_gen.COVERAGE` — see
"cylon" below) but builds the same way; it needed no other Makefile
change because its `.hex` conversion is the same `bin2hex()` path every
other image already uses.

**Flash.** The brief's suggested invocation was
`openFPGALoader -b ecp5_versa build/dino_<tag>.bit`. That board name does
**not exist** in this session's toolchain — verified, not assumed:

    $ ~/oss-cad-suite/bin/openFPGALoader --Version
    openFPGALoader v1.1.1
    $ ~/oss-cad-suite/bin/openFPGALoader --list-boards | grep -i versa
    certusnx_versa_evn         ft2232             Undefined
    certuspronx_versa_evn      ft2232             Undefined

Those are Certus(-Pro)NX Versa eval boards — a different Lattice family,
not the ECP5-5G Versa this repo targets. `--list-boards | grep -i ecp5`
shows only `ecp5_evn` (the ECP5 Evaluation Board, a different board with
its own FTDI channel mapping) and `ecp5_generic` (cable `Undefined` —
still needs `-c`). **There is no `-b` board name for this exact board in
v1.1.1.** Flash by cable instead — the board's on-board FT2232H JTAG/UART
bridge is the same chip family `ecp5_evn` uses, and openFPGALoader
resolves the actual part over JTAG regardless of board name:

    make prog IMAGE=<tag>                                   # build + SRAM load (volatile, bring-up default)
    make prog-flash IMAGE=<tag>                             # build + SPI FLASH write (survives power cycles)
    openFPGALoader -c ft2232 build/dino_<tag>.bit          # same load, by hand; SRAM config (default; no flash wear)
    openFPGALoader -c ft2232 --detect                       # sanity-check the cable/IDCODE first

Confirm the cable choice with `--detect` before the first real flash of a
session — if it reports no device, `-c ft4232` is the other FTDI part
oss-cad-suite ships a definition for and worth trying before assuming a
hardware fault. **Fallback: `ecpprog`** (also in `oss-cad-suite/bin`,
confirmed present and runnable this session), which talks to the FTDI
part directly with no board-table lookup at all:

    ecpprog -S build/dino_<tag>.bit         # SRAM programming, volatile, same intent as -m

Both defaults are **SRAM**, not flash — a power cycle or board reset
reverts to whatever was last written to flash (nothing, on a fresh
board), which is the right default for bring-up iteration. Add
`-f`/`--write-flash` (openFPGALoader) only once an image is meant to
survive a power cycle.

## What OB/LEDs should show

`ob_led` is dino_core's native active-HIGH OB byte — same sense the
bench LEDs already read. The Versa board's physical LEDs are
active-LOW (illuminate when driven LOW, per the EB103/EB98 User Guide),
and `versa_top.vhd` inverts exactly once at the boundary
(`led <= not ob_led`), so **the net effect is active-HIGH: LED ON means
OB bit = 1**, matching the bench convention — no extra bit-flipping in
your head at the bench.

Pin identity (`fpga/top/versa.lpf`, `fpga/top/versa_top.vhd` port
comment):

    led[0] E16   led[1] D17   led[2] D18   led[3] E18
    led[4] F17   led[5] F18   led[6] E17   led[7] F16

Per-image finals, generated by (added this task; was absent before):

    python3 docs/notes/progrom_gen.py --expected


## DIP sweep table — `PROG_in`

Polarity is a **documented decision**, not a guess (`versa_top.vhd`
header, cross-checked against the EB103/EB98 User Guide): the Versa DIP
switches read LOGIC LOW in the "ON" (down) position — pulled to ground —
and LOGIC HIGH ("OFF"/up, pulled up). That is the *same* convention the
real bench's SW1 uses (`docs/notes/progrom_gen.py`'s `IN` comment:
"SW1 IS ACTIVE LOW... a CLOSED switch pulls its bit LOW"), so
`versa_top.vhd` wires `dip_sw => dip` with **no inversion**, and
`fpga/sim/test_module_input_output.py`'s header confirms `input_output.vhd`
itself has no inverter on this path either — the byte `dino_core` reads
off the switches is the raw electrical pattern, ON=0/OFF=1 per bit.

Physical DIP settings for the two bench-anchored values (dip[0]=H2 ...
dip[7]=K20, `fpga/top/versa.lpf`):

    target 0x01 (-> OB 0x30):   dip[0]=OFF  dip[1..7]=ON
    target 0x1E (-> OB 0x4D):   dip[0]=ON  dip[1..4]=OFF  dip[5..7]=ON

**Expected case:** flash `dino_in.bit`, set the switches per the table
above, press reset. OB should read the target value (0x30 or 0x4D per
the table), matching the bench's own confirmed readings (CLAUDE.md:
"SW1=0x01 gives 0x30, SW1=0x1E gives 0x4D").

**Failure symptom — "all bits read inverted":** if every DIP setting
produces the bitwise-complement answer (e.g. the 0x1E setting above
yields OB from `0x2F + 0xE1 = 0x10`, not `0x4D`), the polarity guess in
`versa_top.vhd`'s header was wrong for this board revision. **The fix is
named in that file's own comment: change `dip_sw => dip` to
`dip_sw => not dip` in `versa_top.vhd`, and update the comment — do not
invert anywhere inside `dino_core`.** A single-bit-wrong (rather than
all-bits-wrong) symptom is a different fault (one DIP line stuck or
swapped) and is a wiring/pin question, not a polarity one.

## Reset and the poison discipline — FPGA differs from the bench here

`btn_reset_n` is the Versa `rst_n` push-button, site T1
(`fpga/top/versa.lpf`), ANDed inside `versa_top.vhd` with `pll_locked`
(`core_rst_n <= rst_n and pll_locked`) so the machine cannot execute
against a clock that has not yet met its constraint — a concern the
bench has no equivalent of (Y1 is either running clean or not powered at
all).

**The FPGA powers up clean.** Unlike the bench (U35 has no reset, so OB
always already holds the *previous run's* answer and a power-cycle does
not clear it — CLAUDE.md), the FPGA's `ob_led` register is a real
synchronous register that resets to `0x00` on power-up / `btn_reset_n`
assertion. This makes the milestone's leading `LDAI 0xFF; OUT` poison
step **directly observable** where the bench can only infer it: watch
`dino_real.bit` run and you should see all LEDs OFF (0x00, power-up),
then all LEDs ON (0xFF, the poison write), then the milestone pattern
(0x4D) settle in — three distinct states, not two. A run that shows only
0x00 -> 0x4D (skipping the all-ON poison flash) did not really execute
the poison step and is a finding, not a shortcut worth taking as a good
sign.

## Run order — mardisc before loop

Same doctrine as the bench (CLAUDE.md, 2026-08-04): `mem` proves RAM
round-trips through *one* address (`0x8000`, bit 15 alone) and is
therefore blind to whether MAR's low byte actually discriminates
addresses — a MAR_LO stuck bit would still pass `mem`, because the store
and the load use the identical address. `mardisc` asks the question
`mem` structurally cannot: two STAs to addresses differing only in
MAR_LO, then a read-back of the first. Run `mardisc` (OB should read
`0x6B`) **before** `loop` (which depends on RAM addressing already being
trustworthy) in any coverage sweep, fabric included.

## Machine rate — 120 kHz in fabric, 1.024 MHz on the bench

`fpga/top/versa_top.vhd`'s own header derives it: `clk_sys` is the
EHXPLLL PLL output at 12 MHz (`ecppll -i 100 -o 12`, verbatim divisors);
a `/25` divider (unchanged from the bench-rate Task 13 draft) produces
`clk4m_y1`, and `dino_core`'s own U20 (`'163`) divides that by 4 again —
so **machine CLK = clk_sys / 100 = 120 kHz**, versus the bench's Y1-fed
1.024 MHz. The chain is confirmed in the build logs, not just the
comment:

    $ grep "Max frequency" fpga/build/dino_real.pnr.log | tail -1
    Info: Max frequency for clock '$glbnet$clk_sys': 16.82 MHz (PASS at 12.00 MHz)

Behaviour is **identical** at any rate — the machine is fully static
(CLAUDE.md's own invariant: everything that changes state commits on CLK
low, and nothing in the design depends on an absolute frequency). The
one human-visible difference is `cylon`'s sweep rate. From
`docs/notes/progrom_gen.py`'s own T-state accounting for one outer LED
frame (`outer iteration = 4102 T`, `CYLON_OUTER_N = 25` outer iterations
per frame, 14 frames per sweep — comments in that file, not re-derived
here):

    bench (1.024 MHz, T=976.6ns):  102,550 T/frame -> ~100 ms/frame, ~1.4 s/sweep
    fpga  (120 kHz,   T=8333.3ns): 102,550 T/frame -> ~855 ms/frame, ~12.0 s/sweep

(ratio 1.024 MHz / 120 kHz = 8.53x slower — the LED sweep is a visibly
lazier cylon on the Versa board than on the bench, nothing more.)

## cylon — the victory lap, fabric edition

`cylon` is **not** in `progrom_gen.COVERAGE` (it never halts, so it has
no `(OB, ends)` fingerprint — `progrom_gen.py`'s own comment) and
therefore has no sim test and no entry in the `--expected` table above —
there is nothing for an oracle to check, only something to *look at*.
`roms/PROG_cylon.bin` already existed (bench-burned 2026-08-04); this
task proved the FPGA path is equally trivial — `make -C fpga bit
IMAGE=cylon` needed only a `HEX_cylon`/`bin2hex()` line, no VHDL or
Makefile-logic change, and built clean:

    $ make -C fpga bit IMAGE=cylon
    ...
    timing gate: Max frequency for clock '$glbnet$clk_sys': 16.82 MHz (PASS at 12.00 MHz)
    built .../fpga/build/dino_cylon.bit

Flash it, watch one LED walk out and back across the bar (per
`CYLON_FRAMES`) at the ~855 ms/frame rate above, forever. It never
halts by design — that is the soak: if it is still sweeping clean an
hour later, the fabric survived an hour of continuous free-running
execution with no static hazard tripping the invariant monitor's
equivalent in real silicon.

## What the fabric tells the bench

Three things the FPGA can say that the bench, by its nature, cannot.

**a. HALT-hold is a marginal-level question, not a logic question.**
CLAUDE.md's open item 1: on the bench, `PROG_flow`'s HALT escapes after
a few seconds, "varying" — suspected marginal analog level (`W` 2.26V,
`PC_MAR_MUX` 1.0V avg), not a logic fault, because `CET` is sampled every
clock and a level that reads as a clean 1 to a probe can still be
marginal to a real gate. **Fabric has no marginal levels** — every net
is a rail-to-rail LVCMOS driver inside the FPGA fabric, so this is a
clean discriminator: flash `dino_flow.bit`, let it HALT (OB settles at
`0x39` per the table above), and watch. HALT is not pinned out (`halt_nc`
in `versa_top.vhd` — deliberately NC, see that file's header), so the
observable is **LEDs frozen at `0x39` with no further activity** — no
flicker, no drift, indefinitely. If the FPGA HALT holds forever while the
bench's own HALT still escapes, the bench escape is confirmed analog
(a real marginal level on real silicon), not a latent logic bug the
netlist itself carries — the fabric IS the netlist with no analog
margin question at all. `cylon` is the deliberate contrast case in the
same table: it never halts by design, so it should never freeze, and a
frozen `cylon` display is itself a fault report.

**b. A dropped-copper-class bug cannot exist in fabric.** The 2026-08-04
MAR_LO investigation's headline finding was a board-to-board wire that
was never driven by any test and never sampled by any test — "the wire
between two proven modules is checked by nothing" (CLAUDE.md). That
class of bug is specific to *physically separate boards connected by
hand-run wire*; `fpga/top/versa_top.vhd` and the generated `fpga/gen/*`
sheets are ALL compiled from the SAME netlist source `kicad_contracts.py`
already walks, with every internal net resolved by the synthesis tool,
not a human with a wire strip. **The FPGA is the reference
implementation of the netlist.** If an image behaves correctly in
fabric but disagrees with the same image on the bench, the fabric result
is the one to trust first, and the divergence points at bench board
wiring (the nine-wire class), not at a netlist encoding error — the
netlist-integrity gate (`docs/notes/test_netlist_integrity.py`) already
rules out the synthesis-side version of "a wire quietly disappeared."

**c. The flow/loop FLAG_Z race was a MODEL bug, and the FPGA is not
where to re-litigate it.** When `SUB; JNZ` first ran on real copper
(2026-08-04, flow green), it worked. `fpga/sim/test_core_coverage.py`'s
own header documents that its FIRST run of the equivalent sim images
FAILED — a tick-count mismatch between `ttl_74ls273.vhd`'s (`FLAG_Z`)
and `ttl_74ls373.vhd`'s (`TMP_A`/`TMP_B`) own edge-detect stages, fixed
in the TTL *model*, not in any real gate (task-12-report.md's
adjudication, "bench + LA capturing FLAG_Z/n_clk/w"). The optional **LA**
(DSLogic, 16ch, relative-timing capture — the right instrument per
CLAUDE.md's own taxonomy: the LA answers WHEN, a scope answers HOW/analog,
and this is a 6-pin ns-relative-timing question, not an analog one) check
for extra margin on real copper — confirming `Z` falls **>= 20 ns** after
`~CLK` rises, at `U27.5`/`U27.6`/`U49.5`/`U53.8`/`U45.11`/`U38.8` —
remains available and worth doing on the bench for margin, but it is not
a required gate: the
fabric build already re-runs the SAME (now-fixed) model through
`fpga/sim/test_core_coverage.py`'s `flow_takes_the_jump_and_falls_through`
and `loop_takes_the_jnz_branch` tests, oracle-checked, and both pass.

## Known accepted items

**594 hold violations, all −0.18 ns**, identical across task-13-report.md's
six original image builds ("Gate 4") — four of those build logs
re-confirmed at this final review; not independently re-verified for the
three coverage images (`mardisc`, `pads`, `cylon`) added afterward, though
nothing about the mechanism gives reason to expect them to differ. All
attributed by class-and-mechanism to `--ignore-loops`' own zero-delay
pseudo-launch at the cut point of the five dynamic-direction `'245` bus
loops (U25 the MDR bridge, U41 registers A/B, and three more of the same
shape) — every printed hold path LAUNCHES from a fake 0.00ns pseudo-source
at the loop-break combinational cell itself (mdr's U25, x8; registers_a_b's
U41, x2) and CAPTURES at a REAL flip-flop's D input (U18/U31/U32/U33's
`held_TRELLIS_FF_Q_*`) — a fake launch paired with a real capture means no
genuine launch-to-capture pair exists in the first place, not merely that
the path is short — and none of it moves with the PLL frequency setting.
**Accepted provisionally at bring-up; a
structural fix (the "sanctioned enable-mux fallback" task-13-report.md
names but did not judge necessary) is available if board behavior ever
disagrees with sim over this class of net.** Not re-litigated here —
Rico's decision is still pending, per that report's own self-review.

## Reproducibility — one command, most of the gates

`make -C fpga bit IMAGE=<tag>` runs, on **every** invocation:

1. **hex-vs-roms staleness check** (`synth/check_images.py --hex $*`) —
   fails loudly if `fpga/sim/hex/*.hex` is stale relative to the
   committed `roms/*.bin`, with the exact regenerate-and-rebuild command
   printed.
2. **synthesis** through the bus-resolution pre-pass
   (`synth/bus_resolve.ys` — read that file for the tri-state repair
   story) and `--ignore-loops`/`--timing-allow-fail` place-and-route.
3. **the timing gate** — re-reads the FINAL (post-route, not the earlier
   post-place estimate) `Fmax` line for `clk_sys` out of nextpnr's own
   log and fails the build outright unless it says `PASS` at the
   `versa.lpf`-declared 12 MHz constraint.

Three gates are **not** part of every `bit` invocation and need a separate
call — stated plainly rather than folded in, since they are not actually
wired into the Makefile recipe:

- `make -C fpga check-images` — the SLOW `--meminit` gate: synthesizes
  each tag through the full production sequence and compares the
  synthesized `$mem_v2` INIT content against `roms/*.bin` byte-for-byte
  (nine full syntheses; not a `bit` prerequisite on purpose).
- `pytest docs/notes/test_netlist_integrity.py` — the netlist-integrity
  gate (severed-signal census + `$memrd_v2` count against `dino_core`
  directly, not `versa_top`). Run once per change that could affect
  synthesis import, not once per `bit` invocation — it does not depend
  on which `IMAGE` tag is selected.
- `make -C fpga/postsynth` — **gate 5**, the post-synthesis netlist sim:
  runs dino_core through the SAME coarse-stage `synth_ecp5` +
  `bus_resolve.ys` sequence `bit` uses, writes it out as flat Verilog (no
  VHDL anywhere), and re-runs the milestone program under Icarus,
  asserting OB=0x4D against what synthesis actually produced rather than
  the source VHDL. This is the gate that would have caught Task 13's
  CRITICAL FINDING (`opt_clean` eating the program ROM and RAM) directly,
  instead of downstream at place-and-route. Not a `bit` prerequisite for
  the same reason check-images isn't: worth running once per
  synthesis-affecting change, not once per tag.

Together, the five gates are the reproducibility story: one `make bit`
call proves an image is fresh, timing-clean, and reaches `ecppack`; the
other three are cheap enough to run once per synthesis-affecting change
and expensive enough not to want them serialized into every single-tag
build.

## Verification -- `make -C fpga verify`

The gates above prove one bitstream reproduces from source. A separate,
cheap stack proves the *design behind the bitstream* stays correct as it
evolves -- differential fuzzing against the Python oracle, plus the full
cocotb TB ladder, in one command. `make -C fpga verify` runs it
cheapest-first so a red step is found fast, and fails loud at the first
one:

    $ make -C fpga verify
    ...
    === VERIFY: ALL GREEN (137s wall) ===

**137s wall (~2.3 min), exit 0, three stages, all green** (this task's
own run). In order:

1. **Host suite** -- `python3 -m pytest docs/notes/ -q` -> **147 passed**,
   **~52s**. Every `docs/notes/test_*.py`: microcode/progrom encoders,
   the netlist oracle, `fuzz_gen.py`'s own structural-guarantee tests, and
   the VPLAN guard (`test_vplan.py`).
2. **Fuzz** -- `python3 fpga/sim/test_core_fuzz.py`, `DINO_FUZZ_N` seeds
   (default **20**) of `fuzz_gen.gen(seed)`'s randomly-generated,
   structurally-guaranteed-to-halt legal programs, run against the real
   `dino_core` elaboration and cross-checked against
   `docs/notes/progrom_gen.py`'s own `simulate()` oracle on three
   observables (final OB, `ram_writes`, `branches_taken` -- not OB alone,
   see `test_core_fuzz.py`'s own header for the MAR-as-a-latch blind spot
   OB-only would miss). Switches on `IN`-using programs are drawn
   per-seed from `fuzz_gen.gen()`'s own RNG (`meta["switches"]`), not a
   hardcoded value. This task's own run: **20/20 PASS, 14.9s wall**.
3. **cocotb TB ladder** (`fpga/run_cocotb_ladder.sh`) -- 18
   `fpga/ttl/test_*.py` chip-model invocations, 9
   `fpga/sim/test_module_*.py` sheet-model invocations,
   `test_core_milestone.py`'s 2 whole-core cases, and
   `test_core_coverage.py`'s 8 coverage-image cases: 37 `make`
   invocations total (one per MODEL/MODULE_UNDER_TEST/TESTCASE
   combination -- there is no all-models target in `fpga/ttl/Makefile` or
   `fpga/sim/Makefile`, and ROM content is a GHDL generic fixed at
   elaboration, so each `dino_core` TESTCASE genuinely needs its own
   invocation). These 37 invocations are the SOLE citation for roughly
   half of `docs/notes/dino_fpga_vplan.md`'s rows (sections E/F/L/M plus
   most of section A). This task's own run: **37/37 GREEN, 69s wall**.

**Budgets and soak.** `DINO_FUZZ_N` (env var) sets the seed count; unset
defaults to 20 (the number `verify` runs). `DINO_FUZZ_N` is a plain env
var, so it threads straight through -- `DINO_FUZZ_N=500 make -C fpga
verify` genuinely does run a 500-seed fuzz stage. For a soak, call
`python3 fpga/sim/test_core_fuzz.py` directly (with `DINO_FUZZ_N=500`
exported) instead, so only the fuzz stage re-runs. `test_core_fuzz.py`'s
own header carries the 500-seed calibration: 500/500 PASS, 275.6s wall
(0.55s/seed), 2500 metavalue warnings (exactly 5/seed, no variance across
all 500 runs) -- that 5/seed floor is what pins
`METAVALUE_PER_PROGRAM_BOUND = 8` above it, so a real per-program
metavalue increase (not run-to-run noise) trips the budget check rather
than silently passing.

**The GAP list.** Not everything is a green check -- `docs/notes/
dino_fpga_vplan.md` is the coverage map: every invariant CLAUDE.md/
`BRINGUP.md`/the design specs claim, mapped to the artifact that would
fail if it were wrong. **67 rows, 5 GAP** (un-policed rules or ledgered
deferrals -- none silent; `docs/notes/test_vplan.py` guards the row/GAP
counts against drift from the table itself). Read it before assuming a
behavior is proven just because `verify` is green -- GREEN means
"everything checked passed," not "everything is checked."

**How to read a failure.** Each stage names a different kind of problem,
and its own artifact says which:

- **Host suite** -- `pytest`'s own `-q` output names the failing test
  file and function directly. A `test_vplan.py` failure specifically
  means the VPLAN table itself drifted (a citation went stale, or a row
  changed status without `KNOWN_GAPS` following) -- a documentation bug,
  not a hardware one.
- **Fuzz** -- a `seed N: FAIL` line, followed by that seed's disassembled
  program listing and the divergent observable (OB / `ram_writes` /
  `branches_taken`). Reproduce with `fuzz_gen.gen(seed)`; shrink with
  `limit=`. A metavalue-budget failure (not a seed FAIL) means some
  program is driving more `'U'`/`'X'` propagation than the calibrated
  5/seed floor -- a real per-program regression, not a threshold that
  needs raising.
- **cocotb TB ladder** -- the failing `make -C ttl`/`make -C sim`
  invocation's own `results.xml` (`fpga/ttl/results.xml` or
  `fpga/sim/results.xml`) names the failing test function; cocotb's own
  console output above it shows the assertion and simulation time it
  failed at.
